# agent-board

> This text was generated by an LLM (cgwalters-bot). cgwalters has not
> reviewed it yet.

agent-board treats a forge's project board as the control plane for a
human, a coordinator and sandboxed agents. The board, its issues and
their pull requests stay the record people read and edit. There is no
server and no database of its own.

It has two halves. Rules with no model in them compare the board with
reality and propose repairs: an item with no status, a finished item
whose issue is still open. Short agent runs do what needs judgment:
triage, priority, a status update. Neither half holds a write
credential. Both produce *safe outputs*, proposals limited to edits of
one project and to opening and closing issues, which a separate job
checks and applies. Anything else, even closing a pull request, is a
typed request to another job that is allowed to do it.

The CLI is meant to feel like part of `gh`:

```console
$ agent-board item list --snapshot fixtures/board.json
$ agent-board reconcile plan --snapshot fixtures/board.json --emit
```

The binary also answers to `gh-agent-board`, so it can be used as a gh
extension.

## State

Early. What exists is the model, one rule, and an offline CLI that reads
a snapshot file. Nothing here talks to a forge yet except the
`test project` lifecycle used by the live tests, which run from
[cgwalters-forge-stage/board-test](https://github.com/cgwalters-forge-stage/board-test)
against throwaway projects in that organization.

[docs/design.md](docs/design.md) has the design and the steps planned.
Agents run through [agentic-job](https://github.com/cgwalters-forge/agentic-job).
The tools this replaces live in
[homegit](https://github.com/cgwalters-bot/homegit) and keep running
unchanged.
