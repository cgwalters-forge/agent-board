# agent-board

> This text was generated by an LLM (cgwalters-bot). cgwalters has not
> reviewed it yet.

agent-board is an early command-line tool that reads a project board on
GitHub, finds where the board has drifted from what actually happened,
and proposes the repairs. It proposes; it does not apply them yet, and it
does not run agents yet.

It is the first piece of a coordinator for coding agents that keeps its
whole record on the forge: the board, its issues and their pull requests
say what is being worked on, whose turn it is and what an agent is
waiting to ask you, with no server to run and no second database to keep
in step with the first.

## Try it

You need Rust. From a clone of this repository:

```sh
cargo install --git https://github.com/cgwalters-forge/agent-board agent-board
export PATH="$HOME/.cargo/bin:$PATH"
```

Then, against the sample board in `fixtures/`:

```console
$ agent-board item list --snapshot fixtures/board.json
ITEM              STATUS  PRIORITY  TURN         TITLE
example/intake#1  -       P2        Coordinator  Repair missing status
example/intake#2  Triage  P1        Coordinator  Already triaged

$ agent-board reconcile plan --snapshot fixtures/board.json --emit
Proposed only; not applied. Independent bounds/check/apply support is required.
{"content_number":1,"content_type":"issue","fields":{"Status":"Triage"},"project":"https://github.com/orgs/example/projects/1","target_repo":"example/intake","type":"update_project"}
```

The first command reads a board. The second finds what is wrong with
it, here an item nobody gave a status, and prints the repair as a
proposal. These commands read a file and write to your terminal: no
credential, no network.

Against a real board you need a token that can read the project and its
issues:

```sh
export GH_TOKEN=...
agent-board project view   --owner my-org --project 7
agent-board item list      --owner my-org --project 7 --status Triage
agent-board reconcile plan --owner my-org --project 7

# Save the board once, then work on the copy with no token.
agent-board snapshot create --owner my-org --project 7 > board.json
agent-board reconcile plan  --snapshot board.json --emit > proposals.jsonl
```

Commands and flags follow `gh`'s: nouns then verbs, `--json` with
`--jq`, the same exit codes. The binary is also built as
`gh-agent-board`, the name `gh` expects of an extension; it is not
published as one yet.

## What it checks

Three rules today, each a plain function from a snapshot to a list of
proposals, so the same board always gives the same answer:

- an item with no status gets a proposed `Triage`;
- an item marked done whose issue is still open: close the issue;
- an issue closed while its item is not done: mark it done.

They only act on items positively known to be issues, and if the
snapshot is incomplete, because a page failed to load, they propose
nothing. On the board this was written for, these three cases were most
of what went wrong: 89 items with no status, 40 finished ones never
closed.

## Where it is going

Keeping a board true takes two kinds of work. Bookkeeping, like the
rules above, needs no model. Judgment does: deciding what a new issue
is, how much it matters, what to tell you this morning. The plan is for
judgment to be a short agent run in a sandboxed CI job, through
[agentic-job](https://github.com/cgwalters-forge/agentic-job), handed
the same snapshot to read.

Both halves end the same way, with *safe outputs*: a list of requests
in the format GitHub Agentic Workflows defined, like the JSON line
above. A separate job checks the list against fixed bounds and applies
it. The bounds are meant to be narrow: edit fields on one project, open
an issue, close an issue. Anything else, even closing a pull request,
is a typed request to a different job that is allowed to do it.

Of this, the rules and the proposals exist. The job that applies them
and the agent runs do not.

## Why not Paperclip

[Paperclip](https://paperclip.ing) is the closest thing to this and it
is much further along: it coordinates agents today. It gives each agent
an identity, a skill that teaches the working loop (check your inbox,
check out a task, work, report) and an API to a board. agent-board
takes that loop from it. The differences are in the design, and they
are the reason to watch one or use the other.

*Where the record lives.* Paperclip keeps tickets in its own database
behind its own interface. Here they are issues on the forge where your
code and reviews already are. You answer an agent's question by
commenting on an issue, and anyone who can read the repository can see
what the agents are doing and why. The cost is that you get the forge's
board, not one designed for agents.

*What an agent can touch.* A Paperclip agent authenticates to
Paperclip's API; what else it can reach depends on the adapter, the
sandbox and how secrets are configured. The agents planned here get no
forge credential at all. They read a snapshot and write proposals, and
a separate checker and applier enforce what is allowed.

*What is running.* Paperclip is a service that stays up and wakes its
agents on a heartbeat. agent-board is a command for a scheduled CI job
and for events, so there is no service of its own to operate. A stuck
CI job is still a stuck job.

If you want roles, budgets and approvals for a team of agents, working
now, use Paperclip. If the idea of agents that work only through your
existing issues and pull requests is what you are after, this is where
that is being built, and today it will tell you what is wrong with your
board.

## What is real today

The model, the three rules, the reader for GitHub Projects, and the
commands above. CI runs them against fixtures on every change.

A live test runs from
[cgwalters-forge-stage/board-test](https://github.com/cgwalters-forge-stage/board-test)
against a project kept there for it: it opens a scratch issue, adds it,
sets a field, reads the board back, checks the plan, then removes the
item and closes the issue. That command does hold a write token, for
that organisation only. Its
[first runs](https://github.com/cgwalters-forge-stage/board-test/actions/runs/37742267130)
were refused by GitHub because the token there cannot yet reach the
project, so it has not passed.

Not built: the job that applies proposals, agent runs for triage and
reporting, asks to the operator, budgets, and any forge but GitHub.
[docs/design.md](docs/design.md) has the design and the order things
are planned in. Nobody but its authors has used it.

The tools this replaces are in
[homegit](https://github.com/cgwalters-bot/homegit) and keep running
unchanged while this one grows up.
