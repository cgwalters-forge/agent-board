# agent-board

> This text was generated by an LLM (cgwalters-bot). cgwalters has not
> reviewed it yet.

agent-board runs a team of coding agents from a project board you
already have. The board on your forge, its issues and their pull
requests are the whole record: what is being worked on, whose turn it
is, what an agent is waiting to ask you. There is no server to run and
no second database to keep in step with the first.

```console
$ agent-board item list --snapshot fixtures/board.json
ITEM              STATUS  PRIORITY  TURN         TITLE
example/intake#1  -       P2        Coordinator  Repair missing status
example/intake#2  Triage  P1        Coordinator  Already triaged

$ agent-board reconcile plan --snapshot fixtures/board.json --emit
Proposed only; not applied. Independent bounds/check/apply support is required.
{"content_number":1,"content_type":"issue","fields":{"Status":"Triage"},"project":"https://github.com/orgs/example/projects/1","target_repo":"example/intake","type":"update_project"}
```

The first command reads a board. The second finds what is wrong with it,
here an item nobody gave a status, and prints the repair as a proposal.
It did not change anything, and it could not have: nothing in agent-board
holds a credential that can write.

## How it works

Two kinds of work keep a board true, and agent-board keeps them apart.

**Bookkeeping has no model in it.** Rules compare the board with what
actually happened and propose the repair: an item with no status, an
item marked done whose issue is still open, an issue closed while its
item says in progress. A rule is a plain function from a snapshot of the
board to a list of proposals, so it gives the same answer every time and
can be tested with a table. If the snapshot is incomplete, because a
page failed to load, the rules refuse to propose anything.

**Judgment is a short agent run.** Deciding what a new issue is, how
much it matters, or what to tell you this morning needs a model. That
runs as a sandboxed CI job through
[agentic-job](https://github.com/cgwalters-forge/agentic-job), is handed
the same snapshot to read, and ends.

Both halves produce the same thing: *safe outputs*, a list of requests
in the format GitHub Agentic Workflows defined. A separate job checks
the list against fixed bounds and applies it. The bounds here are
narrow on purpose: edit fields on one project, open an issue, close an
issue. Anything else is a typed request to a different job that is
allowed to do it. An agent working the board cannot close a pull
request, let alone merge one.

## Why not Paperclip

[Paperclip](https://paperclip.ing) is the closest thing to this, and it
is further along. It gives each agent an identity, a skill that teaches
it the working loop (check your inbox, check out a task, work, report),
and an API to a board. agent-board takes that loop from it. Three things
are different, and they are the reasons to choose one or the other.

*Where the record lives.* Paperclip keeps tickets in its own database
behind its own interface. Here they are issues on the forge where your
code and reviews already are. You answer an agent's question by
commenting on an issue, from your phone if you like, and anyone who can
read the repository can see what the agents are doing and why. The cost
is that you get the forge's board, not one designed for agents.

*What an agent can touch.* A Paperclip agent holds a token to
Paperclip's API and usually runs on a machine with your other
credentials on it. An agent here holds nothing. It reads a file and
writes a file, inside a sandbox, and what it wrote is checked before
anything acts on it. If a hostile issue talks an agent into
misbehaving, the worst it can do is ask for something the bounds refuse.

*What is running.* Paperclip is a service that is always up, with a
heartbeat. agent-board is a command run by a scheduled CI job and by
events. Between runs nothing is running, so nothing can wedge, and the
state it would have to recover after a crash is the board itself.

If you want an organisation chart of agents with roles, budgets and
approvals, working today, use Paperclip. If you want agents that work
through your existing issues and pull requests and cannot do anything
you did not allow, that is what this is for.

## Using it

It is one binary, `agent-board`, and its commands and flags follow
`gh`'s: nouns then verbs, `--json` with `--jq`, the same exit codes. It
is also built as `gh-agent-board`, the name `gh` expects of an
extension; it is not published as one yet.

```sh
cargo install --git https://github.com/cgwalters-forge/agent-board agent-board

# A board on GitHub: an organisation's project, by number.
export GH_TOKEN=...            # read access to the project and its issues
agent-board project view   --owner my-org --project 7
agent-board item list      --owner my-org --project 7 --status Triage
agent-board reconcile plan --owner my-org --project 7

# The same against a saved snapshot, with no credential and no network.
agent-board snapshot create --owner my-org --project 7 > board.json
agent-board reconcile plan  --snapshot board.json --emit > proposals.jsonl
```

`reconcile plan` only ever prints. `--emit` prints the proposals as safe
outputs, one JSON object per line, for a job that applies them.

## What is real today

The model, three rules, the reader for GitHub Projects, and the commands
above. CI runs them against fixtures on every change. A live test
creates a throwaway project in a separate organisation, reads it back,
checks the plan and deletes it; that test is written and has not yet run
against GitHub.

Not built yet: the job that applies proposals, the agent runs for triage
and reporting, asks to the operator, budgets, and any forge but GitHub.
[docs/design.md](docs/design.md) has the design and the order things are
planned in. Nobody but its authors has used it.

The tools this replaces are in
[homegit](https://github.com/cgwalters-bot/homegit) and keep running
unchanged while this one grows up.
